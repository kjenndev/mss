# Public registration and email verification

## Deployment (owner-supervised)

Back up PostgreSQL and preserve the old columns/roles/password verifiers. Rehearse the entire forward migration chain on a restored disposable copy first. `20261003000000_public_registration.js` is additive and forward-only. It leaves existing email NULL and does not alter existing roles, password verifiers or sessions; only the database default for **future** users becomes `user`. Existing admin provisioning remains available without an email address and is not public signup. Do not reset/seed existing accounts.

Set a unique MSS `EMAIL_SETTINGS_ENCRYPTION_KEY`: base64 encoding of exactly 32 random bytes. Store it outside the repository in the owner-only service environment and back it up separately from the database. Do not copy another application's encryption key or ciphertext. Changing/loss of the key makes mail unavailable until the Resend API key is re-entered. Never log either key.

Confirm the sending domain is verified in Resend and that the API key permits that domain. Only then set `EMAIL_VERIFIED_SENDER_DOMAIN` to the exact lowercase sender domain (for example `midnightsoundsyndicate.com`). This is an **operator attestation**, not an API-based verification check; changing the sender to another domain makes registration unavailable. No provider call or real email is made by settings updates or tests.

An admin configures `PUT /api/admin/email-settings` with `enabled`, `from_email`, `from_name`, `reply_to`, `public_url`, optional `api_key`, and optional `clear_api_key`. A submitted `api_key_configured` flag is read-only and ignored. Blank/omitted API key means keep the encrypted value; explicit clear removes it and requires disabled settings. Defaults: name `Midnight Sound Syndicate`, reply-to/public support/privacy contact `support@midnightsoundsyndicate.com`. A sender address is not inferred from the reply-to address. `public_url` must be an exact HTTPS origin without trailing slash, path, credentials, query or fragment; HTTP loopback is allowed only outside production. It never comes from request Host/forwarding headers. Enable requires a decryptable key and all valid settings. The API does not test delivery.

`GET /api/admin/email-settings` returns only enabled/from_email/from_name/reply_to/public_url/api_key_configured. The ciphertext and provider key are stored in a dedicated `private_email_settings` table, never `system_settings` or public settings endpoints. Admin authorization is rechecked under a user row lock for writes, then the session is re-read/locked and ownership/expiry checked. The shared authenticated mutation helper uses user-before-session lock ordering so a reset/logout committed while a request waits cannot authorize a write.

## HTTP contract

- `GET /api/auth/registration-config`: `{enabled,terms_version,privacy_version}`. Both versions are `2026-10-03`, exported by `registration.js`.
- `POST /api/auth/register`: `{username,email}` only. Email is required and normalized with trim/lowercase. This requests a link, not an account or consent. Unknown fields (including password, consent and role/privileges) are rejected. Pending storage contains only id, suggested username, email and expiry; no password or consent state.
- Register and `POST /api/auth/resend-verification {email}` return generic duplicate-safe `202 {message}` without session/token/user. Validation 400, throttling 429, disabled/setup/provider failure 503. Duplicate handling conceals account existence in response content, **not guaranteed constant-time processing**. Username login and uniqueness are case-insensitive while stored spelling is preserved; passwords remain case-sensitive. Emails are case-insensitively unique.
- Email links are `<public_url>/verify-email#token=...`. No GET mutates state. Capture and remove the fragment before router/media rendering; retain it only in memory. `POST /api/auth/verification-info {token}` is a read-only preview (apart from independent admission counters): returns exactly `{purpose:'registration',username}` or `{purpose:'email_change'}`; invalid/expired tokens return 400. It discloses no email, token, account ID or privileges. Preview budgets are separate from activation budgets.
- To finish signup, explicitly `POST /api/auth/verify-email {token,username,password,accept_terms:true,confirm_adult:true,terms_version:'2026-10-03',privacy_version:'2026-10-03',email_alerts_opt_in:boolean}`. The mailbox holder chooses a **new** username/password and fresh consent; the suggested username is editable to recover safely from unsolicited pending requests or username collisions. Password is 5–1024 characters and uses the existing asynchronous scrypt verifier. Server timestamps are created only at completion. Terms/adult assent must be true; optional alerts are a separate explicit boolean (UI default false). Age is an 18+ self-attestation, not identity verification. No initiator password/preferences exist to inherit. User role is always explicitly `user`.
- For email change, `POST /api/auth/verify-email {token,current_password}` additionally requires Bearer authentication for the exact account that initiated the token and its current password. Anonymous, wrong-account, stale-session or credential-changed requests cannot bind an unsolicited mailbox. Success is `200 {success:true}` without automatic login; invalid/expired/replayed/conflicting requests return 400, missing/revoked session 401, wrong account or disabled account 403. Issued tokens continue to work when mail sending is later disabled.
- `GET /api/auth/me` and successful profile updates expose `email`, `email_verified_at`, and `email_alerts_opt_in` only to the authenticated account. `PUT /api/auth/me` retains username/password/display_name and permits boolean email_alerts_opt_in. It rejects direct email, role, verification and consent fields. Opt-in requires an existing verified email; opt-out writes a server timestamp.
- `POST /api/auth/email-change {email,current_password}` requires an active account/session. Old email and verification remain in force until the new address is verified. Credential, username or email changes invalidate outstanding change tokens; disabled/deleted users cannot complete them. To retry a failed change email, repeat this authenticated request, not anonymous resend.
- New event creation is artist/admin only and rechecks that role inside the existing atomic mutation transaction. Previous event ownership editing is preserved.

## Persistence, delivery and limits

Signup stores a pending registration, not a user, for 24 hours. Only successful verification creates a user with an explicitly assigned `user` role. A token has 256 random bits; only its SHA-256 digest is persisted and its lifetime is 30 minutes. Tokens are single-use under PostgreSQL locks and unique constraints. Resend rotates the token and invalidates earlier links. Email-change tokens bind the then-current account credentials and require matching authenticated consumption. The database case-insensitive unique index arbitrates competing signups/email changes and admin/profile changes.

Mail is attempted **only after persistence commits**. The fixed HTTPS Resend endpoint has redirects disabled, a 10-second timeout, and a per-token idempotency key. Errors are sanitized. Provider acceptance is not proof of inbox delivery. A failure returns 503 and leaves pending state available for explicit resend. There is no durable mail queue, automatic retry loop, alert sender, or raw-token recovery. After a timeout the provider may already have accepted the previous message; a resend issues a new token and new idempotency key, so a recipient can receive both messages, but only the latest token works. A process crash after commit and before send similarly needs explicit resend. No claims of exactly-once email delivery. Disabling sending stops future admissions; it does not cancel in-flight provider calls using an earlier settings snapshot, or invalidate already-issued verification links.

Shared PostgreSQL admission limits run before scrypt/mail: 20/IP, 5/account, 200/global per 15 minutes. Verify uses its own hashed token account key. Email-change charges both authenticated user ID and normalized destination; the recipient bucket is shared with signup/resend. Verification-info has independent bounded global/IP/token budgets so preview cannot consume activation attempts. Buckets and registration mutations use separate short-lived advisory locks, never the existing upload lock. Hashing and network operations run outside registration locks. Default Express proxy trust remains false: do not trust arbitrary forwarded addresses; deployment operators must plan trusted-proxy configuration before public exposure.

Expired pending records are pruned on subsequent registration admission, cascading verification tokens. Expired email-change tokens are pruned during token issuance. There is no continuous cleanup worker. Audit/retention policy and production mail delivery testing remain deployment responsibilities.

## Isolated tests

Fast suite: `cd mss-api && node --test` (native suite deliberately skips without its explicit disposable database variable).

Windows/WSL native runner, requires local PostgreSQL administration:

```
wsl.exe -d Ubuntu -u root -- python3 /home/kjenn/code/mss/mss-api/test/run-registration-postgres.py
```

The runner copies only source/dependencies into a fresh temporary workspace (excluding environment files, uploads and media), creates a random `mss_registration_test_<uuid>` database, runs real Express HTTP/Knex/PostgreSQL tests with an injected provider, drops the database, checks the catalog count is zero and removes the temporary workspace. It never selects `mss_local`, imports live db.js configuration, restarts services, accesses another application's credentials or sends mail. It requires installed `node_modules`. Native coverage includes the historical migration chain, preservation of an existing account, DB default role, admin settings secrecy, pending signup, consent/privilege rejection, concurrent replay/duplicates, expiry, provider failure/resend, commit-before-send, email change, shared throttles, mailbox-holder-only credentials/fresh consent, read-only purpose preview, disablement with outstanding links, shared recipient limits, and deterministic password-reset/logout interleavings against settings/email-change writes. These races wait for an observed PostgreSQL user-row lock wait before committing revocation. Existing suite covers strong/legacy password login behavior and event atomic reauthorization/profile preference checks.
